# Практика 6. TaskTracker 2.0 — сложные связи в EF Core

## 🎯 Цель

Расширить готовый проект **TaskTracker** так, чтобы он использовал более сложную модель данных в **EF Core**:

- несколько связанных сущностей;
- связи **один-ко-многим** и **многие-ко-многим**;
- enum-поля, ограничения, индексы;
- запросы с фильтрацией и простой статистикой.

Фокус — **работа с базой данных и EF Core**, изменения во вьюхах и контроллерах могут быть минимальными.

---

## 1. Исходные данные

Вам выдан готовый проект **TaskTracker**:

- ASP.NET Core MVC + EF Core + SQLite;
- есть сущность `TaskItem` с базовыми полями
  (например: `Id`, `Title`, `Description`, `CreatedUtc`, `IsDone`);
- настроен `AppDbContext`;
- есть CRUD по задачам: список, создание, просмотр, редактирование, удаление.

**Важно:**
Вы можете изменять код проекта, но в результате работы должен **сохраниться рабочий CRUD по задачам**.

---

## 2. Требуемая функциональность

К моменту сдачи приложение должно поддерживать:

1. **Расширенные задачи**

   Задача хранит:

   - заголовок и описание;
   - дату создания;
   - **крайний срок** (deadline);
   - **статус** (например: запланирована, в работе, выполнена, отменена);
   - **приоритет** (например: низкий, средний, высокий, критичный);
   - признак архивной/удалённой задачи (для возможного soft delete).

2. **Проекты**

   - Задача может принадлежать **проекту**.
   - Один проект содержит **несколько задач**.

3. **Теги**

   - У задачи могут быть **теги**.
   - Один тег может относиться к нескольким задачам.
   - Связь **многие-ко-многим** между задачами и тегами.

4. **Комментарии**

   - У задачи могут быть текстовые **комментарии**.
   - Одна задача содержит **несколько комментариев**.

5. **Запросы и статистика**

   Должны быть реализованы методы (в сервисе/репозитории/контроллере):

   - Получение **последних N задач** с осмысленной сортировкой
     (например: сначала невыполненные, внутри — по приоритету и/или сроку).
   - **Поиск задач** по комбинации фильтров (проект, статус, приоритет, срок, тег).
   - **Статистика по статусам** задач (количество задач в каждом статусе).
   - **Статистика по проектам** (количество задач в проекте, количество выполненных и т.п.).

   Форма вывода (страницы, JSON, простые таблички) — на ваше усмотрение, по согласованию с преподавателем.
   Главное — чтобы запросы **реально работали через EF Core**.

---

## 3. Модель данных и связи

В проекте должны быть реализованы как минимум следующие сущности:

- **TaskItem** — задача.
  - Базовая информация (заголовок, описание, даты).
  - Статус и приоритет (через **enum**-типы).
  - Крайний срок.
  - Признак архивности (для soft delete).
  - Связи:
    - принадлежит проекту (опционально);
    - имеет много тегов (many-to-many);
    - имеет много комментариев (one-to-many).

- **Project** — проект.
  - Название, описание.
  - Связь: **один проект → много задач**.

- **Tag** — тег.
  - Название тега.
  - Связь: **многие-ко-многим** с задачами (через таблицу-связку в БД).

- **TaskComment** — комментарий к задаче.
  - Текст комментария.
  - Дата создания.
  - Связь: **одна задача → много комментариев**.

Требования к модели:

- Использовать **enum**-типы для статуса и приоритета задачи.
- Настроить связи через EF Core (Fluent API и/или атрибуты).
- В базе данных должны появиться:
  - отдельные таблицы для всех сущностей;
  - таблица-связка для связи задач и тегов (many-to-many).

---

## 4. Работа с EF Core и базой данных

Обязательные требования:

1. Приложение использует **SQLite** как постоянное хранилище данных
   (файл базы в проекте, не in-memory вариант).

2. Все сущности подключены в `AppDbContext` через `DbSet<T>`.

3. Все операции с задачами, проектами, тегами и комментариями выполняются через **EF Core**:
   - **нет** главного хранилища данных в виде `static List<>` и т.п.;
   - чтение и запись идут в реальную базу.

4. Изменение схемы базы выполняется через **миграции EF Core**:
   - при добавлении новых сущностей и полей схема базы должна обновляться миграциями;
   - не допускается «ручное правление» схемы БД в обход EF Core.

5. DI и архитектура:
   - `AppDbContext` регистрируется через `AddDbContext` в `Program.cs`;
   - зависимости (контекст, репозитории, сервисы) передаются **через конструктор**.

---

## 5. Запросы и фильтрация

В проекте должны быть реализованы методы (подходящий слой на ваше усмотрение):

- Получение **последних N задач** с сортировкой по:
  - статусу (например, невыполненные выше выполненных),
  - приоритету,
  - дате создания/дедлайну.

- **Поиск задач** по нескольким фильтрам. Примеры параметров:
  - проект;
  - статус;
  - минимальный приоритет;
  - срок (задачи с дедлайном до определённой даты);
  - тег.

  Если параметр не задан — соответствующий фильтр не применяется.

- **Статистика по статусам**:
  - количество задач в каждом статусе.

- **Статистика по проектам**:
  - количество задач в проекте;
  - количество/доля выполненных задач.

Форма выдачи (страница, JSON, простое текстовое представление) — на ваше усмотрение.
Главное — корректная логика и использование LINQ/EF Core.

---

## 6. Дополнительно (по желанию): soft delete

Необязательное, но желательное улучшение:

- Реализовать **«мягкое удаление»** задач:
  - задачи помечаются как архивные с помощью логического поля;
  - при обычных запросах архивные задачи не отображаются;
  - физически записи остаются в базе данных.
- Можно использовать глобальный фильтр EF Core (`HasQueryFilter`), либо явную фильтрацию во всех запросах.

---

## 7. Критерии оценки

Работа считается выполненной, если:

1. Проект **успешно собирается и запускается**.
2. CRUD по задачам (`TaskItem`) продолжает работать:
   - список задач,
   - создание,
   - просмотр,
   - редактирование,
   - удаление (или архивирование — если реализован soft delete).
3. В базе данных:
   - есть таблицы для `TaskItem`, `Project`, `Tag`, `TaskComment` и таблица-связка для тегов;
   - корректно настроены связи между сущностями.
4. Используется **EF Core + SQLite**, нет основного хранилища в памяти.
5. Изменения схемы БД выполнены через **миграции EF Core**.
6. Запросы для фильтрации и статистики работают на реальных данных и выдают логичный результат.
7. (Бонус) Реализован soft delete: «удалённые» задачи не показываются пользователю, но остаются в базе.
